# Парсер цін зі сповіщеннями в телеграмі

Стежить за цінами товарів, які люди надсилають боту посиланням, і пише, коли
ціна **справді** впала.

«Справді» — це нижче звичної ціни товару, порахованої за всією його історією,
а не нижче перекресленої ціни на сайті: її магазини накручують. Звичною
вважається мода — найчастіша ціна в історії, згрупована по кошиках. Мода тут
не випадкова: мінімум ловить разовий викид, середнє розмивається будь-яким
стрибком, а мода показує ту ціну, яку товар має зазвичай.

Про одну знижку бот каже один раз, а не щодня, доки вона триває.

## Як це працює разом

```
бот         ←→  людина надсилає посилання, отримує сповіщення
   ↓
парсер          кожні 6 годин обходить магазини, пише ціни в SQLite
   ↓
детектор        рахує моду по добових зрізах, шукає падіння нижче порогу
   ↓
розсилка        пише підписникам; про надіслане пам'ятає журнал
```

Плюс дві речі, які роблять систему такою, що переживає тиждень без нагляду:
**здоров'я магазинів** (магазин мовчить дві доби — власник дізнається) і
**автооновлення коду** (`git push` → сервер сам підтягує, ганяє тести й
перезапускається).

У `.env` мінімально потрібні `TELEGRAM_BOT_TOKEN` (від @BotFather) і

повідомлення. Схема бази підніметься сама при першому запуску.

## Запуск

Бот — єдиний процес, який має працювати постійно:

```bash
python run_bot.py
```

Обхід магазинів. Адреси беруться з бази — тобто саме те, що люди додали через
бота:

```bash
python run_parser.py --all
```

Показати, кому що пішло б, **нічого не надсилаючи**:

```bash
python run_notify.py
```

Справді надіслати:

```bash
python run_notify.py --send
```

Подивитись на знижки очима, без телеграму:

```bash
python run_discounts.py --everything
```

Локальна панель — http://127.0.0.1:8010 :

```bash
python run_web.py
```

Порядок для одного циклу: `run_parser.py --all`, потім `run_notify.py --send`.
На сервері це роблять таймери — див. [deploy/README.md](deploy/README.md).

### Прапорці, які знадобляться

`run_parser.py`:

| Прапорець | Призначення |
|---|---|
| `--site <slug>` | конкретний магазин (можна кілька разів) |
| `--all` | усі активні |
| `--dry-run` | без запису в БД |
| `--limit N` | максимум товарів на сайт |
| `--from-code` | брати адреси зі списку в коді, а не з бази |
| `--log-level DEBUG` | детальні логи — головний інструмент при розборі збою |

`run_discounts.py` рахує моду на трьох рівнях: `--modes` (кожен товар окремо),
`--basket` (набір товарів як ціле), `--assortment` (весь магазин), а також
`--index` і `--groups`. `--everything` показує все одразу.

`run_notify.py`: `--send` (надіслати), `--all-products` (враховувати й те,
чого немає в наявності), `--anytime` (надіслати попри тихі години),
`--skip-health` (не перевіряти магазини).

## Постійна робота

Система живе на домашньому сервері під Proxmox: бот на polling, SQLite на
диску, публічної адреси не потрібно. Розгортання, служби systemd, бекапи й
автооновлення описані окремо — [deploy/README.md](deploy/README.md).

Розклад там такий: обхід о 00, 06, 12 і 18 годині, розсилка о 07, 13 і 19,
бекап о 03:00, перевірка оновлень щогодини.

Розсилка лише денна навмисно. Магазинам байдуже, котра година, а людям ні:
знижка, знайдена нічним обходом, о сьомій ранку нікуди не подінеться — вона
триває днями. Нічне сповіщення нічого не рятує, зате будить. Те саме правило
продубльоване в коді (`NOTIFY_QUIET_FROM` / `NOTIFY_QUIET_TO`, типово
22:00–08:00), щоб воно діяло й при запуску руками.

Години рахуються за **місцевим часом машини**, а свіжий контейнер Linux стоїть
у UTC — часовий пояс на сервері треба поставити явно.

## Якщо щось пішло не так

Перше правило: **подивитись у журнал**, а не вгадувати. Кожен канал пише свій
файл у `logs/` — `parser.log`, `notify.log`, `bot.log`, `discounts.log`.
Історія обходів одним рядком на прогін:

```bash
grep "Прогін завершено" logs/parser.log | tail -20
```

### Бот мовчить

Перевірте, що процес живий (`systemctl status pricebot` на сервері) і що в
`logs/bot.log` є рядок `Start polling`. Якщо процес падає одразу — майже
завжди це порожній або зіпсований `TELEGRAM_BOT_TOKEN` у `.env`.

### Сповіщення не приходять, хоча ціна впала

Найчастіша причина — **історії ще замало**. Звична ціна рахується мінімум за
`DISCOUNT_MIN_SAMPLES` **днями спостережень** (типово 5): не замірами, а саме
днями, бо обхід іде чотири рази на добу і мода не має залежати від того,
скільки разів ми зазирнули в магазин.

Друга причина — про цю знижку вже казали. Про один епізод бот каже один раз;
винятки лише два: знижка поглибшала або ціна відновилась і впала знову.

Третя — зараз тихі години (типово 22:00–08:00 за місцевим часом машини).
Розсилка в такий час нічого не надсилає й нічого не запам'ятовує: найближчий
денний прогін надішле ту саму знижку як звичайну новину. Надіслати попри це —
`--anytime`.

Подивитись, що система бачить, нічого не надсилаючи:

```bash
python run_notify.py
```

```bash
python run_discounts.py --modes
```

### Магазин перестав читатися

Про це не треба здогадуватись: якщо магазин мовчить `HEALTH_SILENT_DAYS` доби
поспіль (типово 2), власник отримує повідомлення — з назвою, кількістю товарів
без нагляду й текстом останньої помилки. Коли магазин оживе, бот напише й про
це.

Причину покаже пробний прогін:

```bash
python run_parser.py --site <slug> --dry-run --log-level DEBUG
```

Найчастіше це змінена розмітка або антибот-захист. Обходити захист у цьому
проєкті не будемо: такий магазин просто вимикається (`enabled = False` у класі
парсера).

### Прогін показує `failed`

Це означає, що не зібралось **нічого й ні з ким**. Один недоступний магазин із
кількох на код виходу не впливає — інакше systemd світив би червоним щодня
через будь-який 403, і на цей колір перестали б дивитись. Частковий збій видно
в підсумку прогону:

```
Нічого не дали: maudau — решта зібралась, прогін не провалено
```

### Люди просять магазин, якого немає

Кожне посилання на невідомий магазин лягає в базу як заявка, а власник
отримує повідомлення. Накопичений попит — команда `/shops` у боті: зверху те,
що просять найчастіше.

### База виглядає порожньою або застарілою

Не копіюйте `data/prices.db` звичайним `cp`. База в режимі WAL, і свіжі
транзакції лежать у `prices.db-wal` — копія вийде старішою за оригінал,
мовчки. Знімати копію треба скриптом:

```bash
python deploy/backup_db.py --dir /tmp/копія
```

### Схема бази не збігається з кодом

Схему веде alembic, і міграції застосовуються самі при старті. Якщо потрібно
вручну:

```bash
python -c "from app.db.migrate import upgrade_database; upgrade_database()"
```

`Base.metadata.create_all` тут не використовується: він створює відсутнє й не
чіпає наявне, тож перша ж правка колонки пройшла б повз базу непомітно.

## Як додати новий магазин

Один файл у `app/parsers/sites/` — реєстр підхопить його сам. Правити ядро не
треба; якщо довелось, це сигнал, що зламалась абстракція.

Порядок перевірки нового магазину, у такій послідовності:

1. **живий запит із коду проєкту** — не очима в браузері й не по `robots.txt`:
   великі магазини України здебільшого за Cloudflare, який дивиться на
   TLS-підпис клієнта, і сторінка, яку показує браузер, парсеру не дістанеться;
2. чи є на сторінці `ld+json` з `schema.org/Product`;
3. чи є в ньому `offers.price`.

Якщо всі три так — беріть `LdJsonProductParser`:

```python
from app.parsers.base import LdJsonProductParser
from app.parsers.registry import register
from app.parsers.throttle import DelayPolicy


@register
class CitrusParser(LdJsonProductParser):
    name = "citrus"
    title = "Цитрус"
    base_url = "https://citrus.ua"
    currency = "UAH"

    # заготовка для ручного прогону: у роботі адреси беруться з бази
    start_urls = ["https://citrus.ua/videokarti/videokarta-msi-...html"]

    delay = DelayPolicy(min_delay=2.0, max_delay=4.0)
```

`ld+json` кращий за CSS-селектори не зі стилістичних міркувань: біля ціни на
сторінці часто стоїть інше число — «кешбек 1 959 ₴», «+0.74 балобонусів», — і
селектор легко схопить саме його. У розмітці ціна названа полем, а не місцем
на сторінці.

Якщо `ld+json` немає, є `HtmlListParser` з CSS-селекторами (`item_selector`,
`price_selector`, `next_page_selector` тощо) — приклад у `_template.py` і в
`demo_books.py`. Точково перевизначаються `extract_price`, `extract_name`,
`parse_card`, `next_page_url`.

Перевірка:

```bash
python run_parser.py --site <slug> --limit 5 --dry-run --log-level DEBUG
```

## Модель паралелізму

* **Між магазинами — паралельно.** `ParserRunner` запускає парсери через
  `asyncio.gather`, кількість одночасних обмежує семафор
  (`MAX_CONCURRENT_SITES`).
* **Усередині магазину — послідовно.** Жодних одночасних запитів до одного
  домену.
* **Затримки.** `DelayPolicy(min_delay, max_delay)` — випадкова пауза перед
  кожним запитом: рівний ритм виглядає як робот.
* **Стійкість.** Ретраї з експоненційним backoff на 429/5xx. Збій одного
  магазину, однієї картки або навіть підготовки парсера не зупиняє решту —
  помилки збираються в `ParseResult.errors` і лягають у журнал прогонів.
* **Запис у БД** серіалізовано окремим локом: SQLite не любить паралельних
  записів.

## База даних

SQLite (`data/prices.db`), схему веде alembic.

| Таблиця | Про що |
|---|---|
| `shops` | магазин: `slug` (= `name` парсера), `title`, `is_active` |
| `products` | товар: `shop_id`, `name`, `url`, `external_id`; унікальність за (`shop_id`, `url`) |
| `prices` | історія: `product_id`, `price`, `in_stock`, `parsed_at` |
| `telegram_users` | хто спілкується з ботом |
| `subscriptions` | хто за яким товаром стежить, з особистим порогом |
| `notifications` | журнал надісланого — щоб не казати двічі про те саме |
| `shop_requests` | заявки на магазини, яких парсер не знає |
| `shop_runs` | коли який магазин востаннє справді читався |

Кожен прогін додає **новий рядок** у `prices` — так зберігається історія.
`STORE_PRICE_ONLY_ON_CHANGE=true` у `.env` змусить писати лише зміни, але
майте на увазі: тоді `parsed_at` перестає бути свідченням того, що магазин
читався (для цього і є `shop_runs`).

Видалення магазину каскадом видаляє його товари й ціни. Товар, прибраний зі
списку однією людиною, з бази не зникає: за ним можуть стежити інші, а історія
цін спільна й цінна сама собою.

### Читання бази напряму

Таблиця `prices` нормалізована — у ній `product_id`, а не назва. Щоб дивитись
історію в DB Browser / DBeaver / `sqlite3`, є два view (дані не дублюються,
рахуються на льоту):

* `v_price_history` — уся історія: `parsed_at`, `product_name`, `shop_title`,
  `price`, `old_price`, `currency`, `in_stock`, `product_url`;
* `v_current_prices` — лише остання ціна кожного товару та її дата.

```sql
SELECT parsed_at, product_name, shop_title, price, currency
FROM v_price_history
WHERE product_name LIKE '%ноутбук%'
ORDER BY parsed_at DESC;
```

## Веб-панель

* `/products` — список із пошуком, фільтром за магазином і пагінацією;
* `/products/{id}` — картка товару з історією цін;
* `/shops` — CRUD магазинів;
* `/docs` — Swagger для JSON API.

## Про відповідальність

Перед парсингом конкретного сайту перевірте його `robots.txt` та умови
використання, тримайте адекватні затримки й не створюйте зайвого навантаження.
Антибот-захист у цьому проєкті не обходиться: магазин, який не хоче бути
прочитаним програмою, просто не береться.
