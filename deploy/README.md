# Розгортання на домашньому сервері (Proxmox)

Проєкт живе на власній машині: код лишається як є, SQLite на диску, бот на
polling. Publicʼної адреси не потрібно — Telegram опитується самим ботом.

Якщо розгортання робить агент (Claude на сервері), дайте йому
[AGENT_SETUP.md](AGENT_SETUP.md): там ті самі кроки з перевіркою після
кожного, місцями, де він має зупинитись і спитати, і правилами, яких він не
порушує — зокрема не правити код на сервері й не бачити токен.

## Чому LXC, а не віртуалка

Для Python-застосунку без власного ядра віртуальна машина — зайвий шар:
окреме ядро, окрема памʼять, повільніший старт. LXC-контейнер ділить ядро з
хостом і споживає стільки, скільки справді треба (тут — сотні мегабайтів).

Знадобиться: **1 vCPU, 512 МБ RAM, 4 ГБ диска**. База росте повільно — один
замір ціни це десятки байтів, тож навіть за роки щоденного стеження за
сотнею товарів рахунок іде на мегабайти.

## 1. Контейнер у Proxmox

У веб-інтерфейсі Proxmox: **Create CT**, шаблон `debian-13` або
`ubuntu-24.04`. Мережа — DHCP, решта за замовчуванням.

Перевірено на Ubuntu 24.04 з **Python 3.12** — це мінімальна версія, на якій
проєкт працює (потрібен сучасний синтаксис типів).

Усередині контейнера:

```bash
apt update && apt install -y python3-venv python3-pip git
```

**Одразу поставте часовий пояс.** Свіжий контейнер стоїть у UTC, а розклад у
systemd і тихі години в боті рахуються за місцевим часом — інакше «07:00»
настане для Києва о десятій ранку, а тиша до 8:00 закінчиться об одинадцятій:

```bash
timedatectl set-timezone Europe/Kyiv
```

```bash
timedatectl
```

## 2. Окремий користувач

Служби не мають ходити під `root` — якщо в парсері колись знайдеться діра,
вона не має відкривати весь сервер.

```bash
adduser --system --group --home /opt/parset_sells pricebot
```

## 3. Код і залежності

```bash
git clone <адреса-репозиторію> /opt/parset_sells
cd /opt/parset_sells
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
mkdir -p data logs backups
chown -R pricebot:pricebot /opt/parset_sells
```

## 4. Налаштування

```bash
cp .env.example .env
nano .env          # вписати TELEGRAM_BOT_TOKEN і TELEGRAM_CHAT_ID
chmod 600 .env     # токен читає лише власник
chown pricebot:pricebot .env
```

`.env` у git не потрапляє — токен доведеться вписати на сервері руками.

## 5. Перенесення наявної бази

Якщо історія цін уже назбирана на іншій машині, **не копіюйте `prices.db`
звичайним `cp`**: база в режимі WAL, і свіжі транзакції лежать у
`prices.db-wal`. Копія вийде старішою за оригінал, мовчки. Знімайте копію
скриптом:

```bash
python deploy/backup_db.py --dir /tmp/перенос
```

Отриманий файл покладіть у `/opt/parset_sells/data/prices.db` — міграції
самі доведуть його до поточної схеми при першому запуску.

## 6. Служби

```bash
cp deploy/systemd/*.service deploy/systemd/*.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now pricebot.service
systemctl enable --now priceparse.timer pricenotify.timer pricebackup.timer
systemctl enable --now priceupdate.timer
```

Що коли працює:

| Служба | Коли | Що робить |
|---|---|---|
| `pricebot.service` | постійно | відповідає в Telegram, приймає посилання |
| `priceparse.timer` | 00, 06, 12, 18 год (±20 хв) | обхід магазинів, запис цін |
| `pricenotify.timer` | 07, 13, 19 год (±10 хв) | розсилка знижок підписникам |
| `priceupdate.timer` | щогодини о :40 (±5 хв) | оновлення коду з git |
| `pricebackup.timer` | 03:00 | копія бази, тримає 14 останніх |

Розкид часу (`RandomizedDelaySec`) навмисний: рівний ритм запитів секунда в
секунду виглядає як робот і дратує магазини.

Обхід іде кожні шість годин, бо знижка живе годинами: при щоденному обході
половину з них видно вже постфактум. Розсилка при цьому лише денна: магазинам
байдуже, котра година, а людям ні. Знижка, знайдена нічним обходом, о сьомій
ранку нікуди не подінеться — вона триває днями, тож нічне сповіщення нічого не
рятує, зате будить. Те саме правило продубльоване в коді
(`NOTIFY_QUIET_FROM`/`NOTIFY_QUIET_TO`, типово 22:00–08:00), щоб воно діяло й
при запуску руками. На «звичну ціну» це не впливає — мода
рахується по добових зрізах, тож `DISCOUNT_MIN_SAMPLES` так і лишається
кількістю днів спостережень, а не походів у магазин.

## 7. Журнали

Крім stdout, який systemd складає в journald, кожен канал пише власний файл
у `logs/`:

| Файл | Хто пише |
|---|---|
| `logs/parser.log` | обхід магазинів |
| `logs/notify.log` | розсилка й перевірка здоров'я магазинів |
| `logs/bot.log` | бот |
| `logs/discounts.log` | ручні прогони `run_discounts.py` |

Файл ріжеться опівночі й тримається `LOG_RETENTION_DAYS` діб (типово 14).
Дублювання з journald навмисне: у journald своя ротація і свої ліміти, а
копію логу зручно віддати або переглянути звичайним `tail`, не згадуючи
синтаксис `journalctl`.

```bash
tail -f /opt/parset_sells/logs/parser.log
grep "Прогін завершено" /opt/parset_sells/logs/parser.log | tail -20
```

Другий рядок — найкоротший спосіб побачити історію прогонів: підсумок
кожного пишеться одним рядком саме для цього.

Вимкнути запис у файл: `LOG_TO_FILE=0` в `.env`.

## 8. Перевірка

```bash
systemctl status pricebot.service
systemctl list-timers 'price*'
journalctl -u pricebot.service -f
```

Разовий прогін, не чекаючи таймера:

```bash
systemctl start priceparse.service
journalctl -u priceparse.service -n 30
```

## Оновлення коду

Ходити до машини на горищі не треба: `priceupdate.timer` щогодини дивиться в
git і, якщо там щось нове, оновлює код сам. Достатньо `git push` — за годину
в телеграмі буде звіт про те, що оновилось.

Не чекати години:

```bash
sudo systemctl start priceupdate.service
```

Що робить `deploy/update.sh`, по порядку:

1. відкладає роботу, якщо саме зараз іде обхід магазинів;
2. `git fetch` і порівняння з `origin/<гілка>` — якщо нового немає, виходить;
3. зупиняється, якщо на сервері є незакомічені правки: перезаписати їх мовчки
   не можна, це єдина копія тієї роботи;
4. `git merge --ff-only`, далі `pip install` — але лише якщо змінився
   `requirements.txt`;
5. міграції бази явно, до перезапуску;
6. **тести**;
7. і тільки після зелених тестів — `systemctl restart pricebot.service`.

Головне тут — сьомий крок. Зламаний коміт не має лишати людей без бота, тож
якщо тести не пройшли, код повертається на попередній коміт (`git reset
--hard`), служби так і працюють на старій робочій версії, а в телеграм
приходить хвіст логу з поясненням. Те саме при невдалій міграції чи
залежностях.

Звіт приходить у будь-якому разі — і про успіх, і про відкат, і про збій.
Мовчання машини читалося б як «усе гаразд», а це найгірше можливе значення
для мовчання.

### Якщо репозиторій приватний

`git fetch` має проходити без пароля, інакше оновлення просто мовчатиме про
збій зв'язку. Найпростіше — ключ розгортання (deploy key) на GitHub:

```bash
sudo -u pricebot ssh-keygen -t ed25519 -f /opt/parset_sells/.ssh/id_ed25519 -N ""
sudo -u pricebot cat /opt/parset_sells/.ssh/id_ed25519.pub
```

Публічний ключ додається в **Settings → Deploy keys** репозиторію (доступ
лише на читання), а адреса origin змінюється на SSH:

```bash
sudo -u pricebot git remote set-url origin git@github.com:<власник>/<репо>.git
```

## Якщо щось пішло не так

**Бот мовчить.** `systemctl status pricebot` покаже, чи живий процес.
`Restart=always` піднімає його сам, але після п'яти падінь за хвилину
systemd зупиняється й чекає на людину — це захист від нескінченного циклу
при зламаному конфізі.

**Сповіщення не приходять.** Перевірте руками, що бачить система:

```bash
sudo -u pricebot .venv/bin/python run_discounts.py --modes
sudo -u pricebot .venv/bin/python run_notify.py      # показ без відправки
```

**Оновлення не приходить.** Подивіться, що каже сам скрипт:

```bash
sudo systemctl start priceupdate.service
journalctl -u priceupdate.service -n 40
```

Найчастіші причини — репозиторій вимагає пароля (див. вище про deploy key)
або на сервері лишились правки, зроблені руками: скрипт навмисно зупиняється,
щоб їх не затерти.

**Магазин перестав парситись.** Про це не треба здогадуватись: якщо магазин
мовчить дві доби поспіль (`HEALTH_SILENT_DAYS`), бот сам напише — з назвою,
кількістю товарів, що лишились без нагляду, і текстом останньої помилки. Коли
магазин оживе, напише й про це. Нагадування про той самий магазин приходить
не частіше ніж раз на добу.

Причину покаже `run_parser.py --site <slug> --dry-run --log-level DEBUG`.
Найчастіше це змінена розмітка або антибот-захист.

Стан магазинів очима, без чекання на розсилку:

```bash
sudo -u pricebot .venv/bin/python run_notify.py    # показ без відправки
```

**`priceparse.service` показує `failed`.** Це означає, що не зібралось
**нічого й ні з ким** — недоступний один магазин із кількох на код виходу вже
не впливає. Інакше systemd світив би червоним щодня через будь-який 403, і на
цей колір перестали б дивитись. Частковий збій видно в журналі прогону
(`journalctl -u priceparse.service`), а якщо магазин мовчить не один день —
про це прийде повідомлення.
